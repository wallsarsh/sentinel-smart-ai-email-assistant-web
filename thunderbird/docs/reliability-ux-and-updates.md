# Sentinel for Thunderbird — reliability, user flows and add-on updates

Design review of commit `2dc1992`, 18 November 2026. The findings below come from tracing the source and installer. They identify reproducible failure paths. A live mailbox trace would be needed to attribute a particular user's missed draft or brief to one of them. All changes described here are proposals.

## Where messages can disappear from the workflow

| Priority and source | Current behavior and user impact | Proposed change |
|---|---|---|
| P0 · [runMonitor](../src/monitor.js), [recentHeaders](../src/background.js) | A successful scan saves an ISO string as `lastScanAt`. The next scan subtracts 300,000 directly from that string, producing an invalid Date. If a folder query rejects, the catch in recentHeaders silently drops that folder. An empty discovery pass can then be recorded as successful. | Parse and validate the stored timestamp before arithmetic, accept legacy numeric values, and use bounded lookback when invalid. Return a result per folder. Advance a folder's checkpoint only after its discovered IDs are durably recorded. Surface partial coverage and retry inaccessible folders. |
| P0 · [pickHeaders and runMonitor](../src/monitor.js) | The monitor selects the newest capped set before removing cached mail. A busy inbox can repeatedly consume the scan limit with the same headers. Moving the lower date bound to the oldest selected header also excludes still older unseen mail. | Separate discovery from AI processing. Page through each folder in bounded chunks, recording pending identities and progress together. Resume by stable date and tie-breaker with overlap and deduplication if a Thunderbird list cursor expires. Rotate folders to prevent starvation. |
| P0 · [createDraftsFor](../src/background.js), [draftEligibility and maybeCreateDrafts](../src/drafts.js) | Only analyses produced in the current monitor pass enter draft selection. With four eligible messages and the default budget of three, the fourth is cached on the next run and never reaches selection. A failed generation or an analysis first produced by the brief can hit the same gap. Bulk retry jobs are separate. | Track draft disposition independently of the analysis cache. Enqueue each eligible analysis once and reconcile recent cached analyses lacking a disposition on upgrade or restart. Apply the draft budget when consuming the queue. Recheck current settings, identity, existing replies and drafts just before saving. Record the reason for every skip. |
| P1 · [refreshBrief and shouldRefreshBrief](../src/brief.js), [scheduler](../src/background.js) | Building overwrites the displayed brief with empty headline/sections during progress. A partial brief dated today can satisfy the freshness check when no new analyses arrive. The dashboard saves the hourly-refresh preference, but the scheduling decision does not read it. A daily wake enters the monitor pipeline, and an overlapping run can absorb another trigger. | Keep the last completed brief visible alongside today's build progress. Include job state, summary completion and retry time in freshness decisions. Persist the daily trigger independently, catch up after sleep/startup, compute the next local-time alarm each day, and enforce the hourly preference separately from the daily and manual triggers. |
| P1 · [refreshBrief](../src/brief.js) | The daily header list is sliced before total coverage is recorded. “Processed all” can mean only the newest capped subset. The smaller selection used for the model summary serves a different purpose. | Discover all in-scope IDs for the day and process them over multiple wakes. Show scanned, eligible, processed, deferred and included-in-summary counts separately. Preserve per-message markers and retry just the summary when its provider call fails. |
| P1 · [runAssistant](../src/background.js) | A thrown draft-stage exception adds a monitor error but returns empty created/failed lists. The final status copies the earlier monitor status, so a healthy scan can hide a failed draft stage. | Persist discovery, analysis, draft and brief outcomes separately. Combine them for display after the run. Include the affected account, recoverable reason and next retry. Keep keys, message bodies and generated text out of diagnostics. |

**Recovery contract.** Give each work item an account-scoped source identity, operation and, for a brief, local-day window. Persist queued, in-progress, saved, deferred or failed state with an attempt count. Resolve transient Thunderbird IDs against the source account after restart. Use a single active worker per item across monitor, bulk and manual entry points. A restart between saving a draft and recording success is ambiguous. Inspect the target Drafts folder for the source reference before retrying. If that check is inconclusive, offer review. For provider outages, back off with a next-attempt time. For denied permissions or an invalid key, pause with a repair action. Respect disabled automation, sender filtering, age limits and existing drafts throughout recovery.

## What users should experience

1. **Set up once.** The [provider form](../src/options.html) already supports loading models and applying a default across features. Keep that flow. From Dashboard, show the next missing step in order: connect a provider, grant host access, choose/test the default model, then select accounts and enable automation. Keep per-feature routing under Advanced. Explain whether the chosen provider is local or remote before the first test. Preserve unsaved input on permission denial.
2. **Know what will run.** The [dashboard](../src/dashboard.html) exposes both “Refresh now” and schedule settings, while the [brief popup](../src/brief.html) offers “Refresh brief.” Use explicit actions such as “Check inbox now” and “Rebuild today's brief.” Show account scope, last successful run and next scheduled run. Distinguish “No eligible messages” from “Inbox could not be read.”
3. **Find a missing draft.** Add a Drafts activity view with Ready to review, Queued, Skipped and Needs attention. Example: “4 eligible · 3 saved · 1 queued for the next run.” Show the individual eligibility reason, open the saved draft directly, and expose Retry only where a repeat could help. Keep every send under the user's control.
4. **Read the brief while it updates.** Display its date and coverage. Example: “Yesterday's completed brief · today's update paused at 18/24 · provider offline.” Offer “Resume” or “Open provider settings” according to the failure. Show available action items even when the final summary is pending.
5. **Move between entry points.** Keep context-menu, popup and dashboard actions attached to the same job. Reopening any view should show its current state and destination. Label buttons for keyboard and screen-reader users, announce stage transitions once, keep focus on the initiating control after completion, and accompany colors with text. Test at 200% zoom and with a long subject line.

## Update from the installation repository

**User flow.** Add an Updates panel in Sentinel Settings with installed version, repository, tracked release channel or ref, last check and “Check for updates.” Show the proposed version and release notes before “Apply update.” Persist pending update state across popup closure. Report success after the new background process confirms its running version. Offer “Later” during active work and distinguish unavailable network, incompatible Thunderbird, pinned install, policy restriction and failed verification.

**Origin and migration.** The [bootstrapper](../../installer/get.ps1) accepts a repository, ref and custom archive URL. The [Windows installer](../../installer/install.ps1) records profile and versions, and the [Node installer](../../installer/install.mjs) can install a local XPI. The [manifest](../manifest.json) currently declares version 0.1.0, a fixed Gecko ID, minimum Thunderbird 140 and no update feed. A profile alone cannot establish which fork supplied its XPI. Have both packaging paths embed the verified source repository, channel/ref, build commit and update-feed URL before signing. A fork must publish its own feed and packages. Follow a branch through versioned builds of that branch. Treat a tag or commit pin as pinned until the user explicitly switches. For legacy, local or custom-archive installs with unknown provenance, show “Update source unknown” and offer a one-time installer upgrade from the user's chosen source. Preserve profile data and the existing add-on ID.

**Publish and check.** Extend the [XPI packager](../../installer/package-xpi.mjs) and release CI to issue monotonically increasing manifest versions, immutable XPI assets, release notes, compatibility bounds and a SHA-256 digest. Publish the channel's HTTPS Gecko update manifest only after the versioned asset is available. Bind the feed to the install origin at packaging time. Build from reviewed commits, verify the signed release or authenticated metadata, and enforce the expected add-on ID, version and digest. A checksum from an unauthenticated source is insufficient. Never pass provider credentials to repository hosts.

**Apply within Sentinel.** Prefer Thunderbird's add-on manager and the packaged Gecko update URL for download, verification and installation. First demonstrate check, stage and apply on the minimum supported Thunderbird 140 and current supported builds, including installer-created profiles with the bundled calendar experiment. Use the documented update-available event and reload when an update has actually been staged. Feature-test manual check support. A metadata lookup by itself does not stage an XPI. If the standard API cannot initiate installation on a supported installer build, prototype a narrowly scoped bundled experiment calling Thunderbird's add-on manager for Sentinel's own ID and recorded feed. Keep the check and apply controls in Sentinel. Respect administrator policy and permission prompts. Temporary developer installs should show their supported reload path. Avoid running git commands or downloaded installer scripts from the extension. [Thunderbird runtime API](https://webextension-api.thunderbird.net/en/mv3/runtime.html#onupdateavailable) · [Mozilla update-manifest format](https://extensionworkshop.mozilla.org/documentation/manage/updating-your-extension/)

**Recover.** Stop claiming new jobs before apply, checkpoint in-flight work, and wait for active draft saves and compose edits to reach a safe point. On startup verify the installed version, migrate stored settings and queue records idempotently, then resume. Keep the previous verified XPI available to the installer for explicit recovery if the new add-on cannot start. Validate storage migration and recovery compatibility before enabling a channel. An offline check or rejected update must leave the working version usable.

## Delivery order and acceptance

| Phase | Verification required before release |
|---|---|
| 1. Repair discovery and draft accounting | Run two consecutive monitor passes against an ISO checkpoint. Make one of two folders fail and verify its checkpoint stays put. Feed more messages than both scan and AI caps across folders with equal timestamps. Let four eligible replies drain across two three-draft runs. Repeat with a brief-cached analysis, a provider timeout and a crash immediately after draft save. Require one saved draft per eligible source or a visible disposition for every exception. |
| 2. Repair brief scheduling and recovery | With the monitor disabled and brief enabled, miss the scheduled time while asleep, then reopen. Exercise simultaneous alarm/manual requests, hourly preference on/off, a local DST change, more than 60 messages and summary-only failure. Require correct daily coverage, one active build, last complete brief readable and eventual completion after recovery. |
| 3. Validate user flows | In a disposable Thunderbird profile, use fixture mail and a controllable provider. Ask a first-time user to finish setup, explain a skipped draft, open a saved reply, and resume a paused brief using keyboard only. Verify labels, focus, progress and status after closing and reopening dialogs. Record platform, Thunderbird version and actual outcomes in the existing manual validation checklist. |
| 4. Ship updates | Install version A from a test fork, publish B there and a different release upstream. From inside Sentinel, check, approve, apply and verify B from the fork. Repeat on the supported installer platforms. Test pinned and unknown origins, no update, corrupt/wrong-ID XPI, duplicate clicks, offline check, managed profile, active draft, restart and installer recovery. Require retained settings and job history, no duplicate drafts and an actionable outcome on every path. |

Use a disposable profile and synthetic mail for reproduction. The first release gate is reliable processing across consecutive scans. Publish the updater only after a real two-version XPI installation passes on supported Thunderbird builds.
